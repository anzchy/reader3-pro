# F-035 Book delete

Ledger row: [F-035](../../../../../docs/feature-ledger.md) (Summary table and the
`#### F-035 Book delete` section). Contract: 018 WI-5 / WI-5c, §6 Q-F and rulings W5-7 – W5-23
in `docs/plans/20260816-tech-stack-migration/tasks/018-library-routes.md`.

## Sub-features

- `GET /api/library` lists the books (`book_id`, `title`, `authors`, `cover_url`, `book_uuid`).
- `DELETE /api/library/{book_id}?delete_conversations=true|false` (default `false`, values
  case-insensitive): 204 with no body; afterwards the book folder, its tombstone
  (`books/.{id}.deleted-*`) and its intent file (`*.intent.json`) are gone.
- `delete_conversations=false` keeps the book's per-book conversations on disk under the
  configured project root, `<root>/{book_uuid}/`; `true` removes them in both places.
- 404 when the book is not in the library (including a second DELETE); 400 for a
  `delete_conversations` that is not a single `true`/`false`, and for a `book_id` that is not a
  `*_data` basename (tombstone names included); 409 with `Retry-After` while another holder has
  the book lock.
- After a delete the book is gone from `GET /api/library`, `GET /api/library/export`,
  `GET /api/library/stats`, the library page and `/read/{book_id}/0` (404).

## How to get to it (user POV)

There is no UI yet: the library card has no delete action (frontend half FB-L18 belongs to
014). A user can only reach it through the API; drive it with the `api` helper.

Never delete `smoke_data` if later steps need a book: build a second EPUB with
`tests/fixtures/epub_corpus.build_epub2` into your own temp dir and `book add --epub` it
(`victim_data` above). The book's `book_uuid` comes from `api GET /api/library`. `conv-body.json`
is a body you write into the evidence folder first, e.g. `{"provider": "ollama", "messages":
[{"id": "m1", "role": "user", "content": "hi"}]}`; the `conversation_id` in the path must be a
uuid. After the `false` delete, `fs ls conversations/<book_uuid>` shows the published file. On
the library page, `$B js` over `[data-testid=lib-book-card]` `data-book-id`s should no longer
list the deleted id.

## Gotchas

- The ledger row is `accepted` with its scope limited to the API route: there is no delete UI
  yet (FB-L18 belongs to 014), so every step here is `api`, not a click. Prove against the WI-5c
  contract.
- The `api` helper shows only `content-type`, `etag` and `location`, so it cannot show
  `Retry-After`. The 409 also needs a lock holder: in the sandbox, a short Python probe that
  takes `fcntl.flock(LOCK_SH)` on `<books_dir>/.locks/<id>.lock` and sends the DELETE with
  `http.client` gives `409`, `Retry-After: 1`, `holder_category: "unknown"` (2026-10-07). That is
  an emulated concurrent holder: label it so, and only ever on the sandbox `books_dir`.
- The project conversation root is `conversations/` beside the sandbox `books/` (the parent of
  `READER3_BOOKS_DIR`), so `fs ls conversations` reads it; it is not the repo's `conversations/`.
- `books/.locks/<id>.lock` stays behind after a delete (seen 2026-10-07). The contract says
  nothing about lock files; it is not a tombstone and is not listed by `GET /api/library`.
- `/api/library/..%2Fetc` is 404 from routing, not the 400 of the id check; use a tombstone-shaped
  id such as `.victim_data.deleted-1` to see the 400.
