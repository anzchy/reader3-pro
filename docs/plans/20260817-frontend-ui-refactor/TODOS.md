## ~~T-7 ｜文字色对比度不达标~~ ✅ 已闭（2026-08-23）

> 原标题是「`--r3-text-quiet` 浅色对比度不达标」。**实测后靶子换了**：`--r3-text-quiet` 本身该删，真正有消费者、真正不合规的是 `--r3-text-subtle`。

- **是什么**（实测重述，2026-08-23）：
  1. `--r3-text-quiet` 全仓库 **0 个 `var()` 消费者**，只在 spec 的三处文字里出现过。亮色下它与 `--r3-text-subtle` 同取 `--p-gray-500`（**完全同值**）；暗色下 `#93a3bb` 与 `--r3-text-muted` `#94a3b8` 的对比度差 **0.01**。两个主题下都是重复角色，是 §11-R7 拆两根轴之前的残留。
  2. 真正的缺陷是 `--r3-text-subtle`（＝原型 `--quiet`，**有**消费者：`.section-eyebrow` / `.count-badge` / `.result-section`）：亮色 `#999999` 在最差底 `#f5f5f5` 上 **2.61**，暗色 `#64748b` 在最差底 `#182335` 上 **3.32**。
  3. 顺带查出阅读轴两处漏网：`sepia` 的 `--r3-page-quiet` `#8a7455` = **3.80**，`green` 的 `#5b7563` = **4.11**，都低于 4.5。
- **裁决**：
  - **删** `--r3-text-quiet`（`:root` 与 dark 两处），文字色 token 从六个减到五个；§3.4 的跨角色前缀禁令同步改「六个 → 五个」。「安静文字」这个角色在阅读轴上由 `--r3-page-quiet` 承担（五个主题都有定义）。
  - `--r3-text-subtle` 提到合规下限：亮色 **`--p-gray-550` `#707070`**（4.54，新增这一档色阶）、暗色 **`#7a8aa2`**（4.50）。
  - `sepia` / `green` 的 `--r3-page-quiet` 提到 **`#7a6449`**（4.78）/ **`#506856`**（4.95）。
  - `--r3-text-disabled` 的 1.47 / 2.08 **明确标注为 WCAG 2.1 SC 1.4.3 豁免**——inactive 组件不受对比度约束，调上去反而让禁用态看着像可用态。写进 spec 是为了防止后来者「顺手修」。
  - 门槛一律按 **4.5** 记，不给大字的 3:1 留口子：§3.4 字阶最大 `xl` 22px 常规字重，够不到 AA「大字」（≥18.66px 粗体 / ≥24px）的定义。3:1 只用于非文字元素（1.4.11）。
- **必须知道的代价**：亮色下 `muted` `#666666`（5.27）与 `subtle` `#707070`（4.54）**只差 0.73，肉眼几乎分不出**。这不是取值没调好——白底 4.5:1 把可用中性灰压死在 `#767676`–`#000` 这一段，原型能在亮色下拉开两级差距**纯粹是因为浅的那级不合规**。结论写进了 spec：**要在亮色下表达第三层级，用字号、字重、留白，不要再调灰度**。暗色底宽松，`6.15` vs `4.50` 是真能看出来的差。
- **落点**：已回写 `spec-frontend-design.md` §3.2（新增 `--p-gray-550`）、§3.3（两个 `:root` 块 ＋ 阅读轴两行 ＋ 新增「文字色实测对比度」表与五条说明）、§3.4（前缀禁令 六→五）。plan 的 **ET-18 关闭**，§1.3 的悬空引用表与 §附录 原型→token 映射表同步标注。WI-10 建 token 层时直接照 spec 抄，无需再定值。

## ~~T-8 ｜z-index 与动效没有 token（缺 §3.5）~~ ✅ 已闭（2026-08-20）

- **是什么**：规格 §3 有颜色、间距、圆角、字阶，**没有** z-index 层级与动效时长／缓动。
- **为什么**：阅读器有四个面板 ＋ 三个覆盖层（工具条／笔记编辑器／tooltip），层级靠字面量必然打架。

- **代价**：新增一节规格。
- **依赖**：**建议在 WI-16 之前**。
- **裁决**：spec 新增 §3.5「层级（z-index）与动效」——9 档 z-index 有序枚举（`--r3-z-base/raised/sticky/panel/overlay/toolbar/popover/toast/skip` = 0/10/100/200/300/400/500/600/700），完整偏序 `base < raised < sticky < panel < overlay < toolbar < popover < toast < skip` 是全站层叠关系的唯一定义；三档动效时长（`--r3-duration-fast/normal/slow` = 150/300/500ms，沿用现有 `--dedao-transition-*` 三档，1:1 无损）＋ 三条 easing。`Modal` 不占 z-index 档（走 top layer）。第 9 档 `--r3-z-skip` 是 8 档定完之后追加的——8 档按 `src/` 归纳，而 `src/` 现状没有跳转链接，漏了原型 `.skip-link`；它不能并进同值的 `toast`（DOM 顺序会让 toast 稳定盖住它，属无障碍回归），必须靠数值赢。
- **落点**：实现归 **WI-10**（ET-19 已从「无 WI」指派给 WI-10）。

## ~~T-12 ｜token 硬编码无守卫~~ ✅ 已闭（2026-08-23）

- **是什么**：仓库**没有任何**机制能验证「no hardcoded magic numbers／100% tokenized」——无 `package.json`、无 stylelint、无 ESLint、无 `.github/workflows`、无 `vite.config.ts`。
- **为什么**：实测硬编码计数——CSS 裸 hex 100 处、`rgba()` 173 处、29 个不同 `font-size` 字面量、19 个不同 `z-index` 字面量、7 个不同 transition 时长；`--r3-*` 与 `--p-*` 落地计数均为 **0**，遗留 `--dedao-*` 620、`--wr-*` 22。没有守卫，token 体系写完也会被绕过去。
- **已做**：plan 的 WI-9 新增了一条「token 硬编码 lint」（与已有的「token 悬空 lint」配对），带只许缩短不许增长的白名单。
- **~~仍开放~~ 裁决（2026-08-23，已问过 Codex 并综合两边）**：选 **stylelint ＋ `stylelint-declaration-strict-value` ＋ `postcss-html` ＋ 一层自写棘轮包装**，不自写 Python 解析。
  - **理由 1（决定性的）**：本条要判的是**复合值与简写**里的字面量（`border: 1px solid #eee`、`box-shadow`、`linear-gradient`、`transition`）。0.8 那条能零依赖是因为 `--x:` / `var(--x)` 两条正则就能穷尽；这条不行，自写等于手搓半个 PostCSS。
  - **理由 2**：「多一份依赖」不是代价——Node 工具链在 WI-9 已是既定成本（`package.json` ＋ Vite ＋ Vitest ＋ jsdom，WI-14 还要 ESLint ＋ dependency-cruiser），B 的零依赖优势在 ET-1 落地那刻归零。
  - **理由 3**：`postcss-html` 是必需项——现状大头样式在 Jinja 模板的 `<style>` 块里（`library.html` 1075 行、`reader.html` 1403 行），不挂 `customSyntax` 等于只扫了 `.css`。
- **Codex 补出的四个坑，全部采纳**（其中第 2、4 条修正了我的初版设计）：
  1. `postcss-html` 看不见 JS 写出去的样式（`el.style.x = "6px"` 等）→ 归 WI-14 的 ESLint AST 规则。**但靶子是"受管属性"不是"所有 `.style` 赋值"**：运行时几何（浮动工具条坐标、进度条宽度、`transform`）是计算值，不该禁。
  2. **`declaration-strict-value` 把「任意 CSS 变量」都算合格**——`var(--dedao-orange)` 会**通过**，620 处遗留引用会全体显示为「已 token 化」，棘轮在迁移开工前就是绿的。包装器必须自己判命名空间：组件侧只许 `var(--r3-*)`，`var(--p-*)` 只在定义 `--r3-*` 时合法。**这条是我没看到的，是本次问 Codex 的净收益。**
  3. `expandShorthand` 不是完整 CSS 语义解析 → **v1 只管明确长属性**，简写逐条纳入且每条先写「合法复合值不误报」的 fixture。（Codex 给的骨架把 `box-shadow` 列进了 v1，与它自己这条警告矛盾，已按它的警告剔除。）
  4. **棘轮比指纹集合不是计数**——只比总数会放过「删一处旧的、在别处添一处新的」。基线是指纹集合，CI 断言 `实测 ⊆ 基线`，基线只许删不许加；**指纹取 `文件:选择器:属性`，不含行号**（行号会被任何无关编辑冲掉）。
- **不与 0.8 的悬空 lint 合并**：两条问相反的问题，且 0.8 必须保持零依赖——它跑在 `.github/workflows/lint.yml` 的 `contracts` job 里，那个 job 不装任何依赖，合并会把 Node 安装拖进最早的 CI。
- **代价**：多一份依赖与配置（已论证不是真代价）；包装器要自己维护命名空间校验与指纹棘轮，约 100 行。
- **背景**：本次审计实测；2026-08-23 Codex 深思（`codex exec`，115k tokens，含 stylelint / postcss-html 上游文档核对）。
- **依赖**：WI-9（`package.json` 得先建出来）。
- **落点**：`plan-frontend-ui-refactor.md` §9.3 新增「工具链裁决」＋「四个必须堵住的坑」两段；WI-9 验收 11 从两个反例扩到**四个**（新增 c. `var(--dedao-*)` 必须红、d. 指纹棘轮不能被等量替换骗过）。
