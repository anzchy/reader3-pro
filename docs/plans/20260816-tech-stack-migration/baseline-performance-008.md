## 0. 怎么重跑


跑完把新 JSON 与旧 JSON 对着看（**比中位数，不比单次采样**）。子命令：

## 2. 六项指标的口径

**两两性质不同，别用同一把尺量。** 每项「测的到底是什么」写在这里，半年后来对比的人靠的
就是这一节。

| # | 指标 | 性质 | 口径 |
|---|---|---|---|
| 1 | 冷启动 | 墙钟 | **全新进程**：解释器启动 → `import reader3_app.web.server` → startup 事件 → 首个请求。**不含 EPUB 解析**（读路径只见 `book.pkl`）。书库固定 20 本 |
| 1b | 大部头入库 | 墙钟 | `process_epub()` 处理一本三百万字符的 EPUB。**含 EPUB 解析与 HTML 清洗**。它不是冷启动的一部分，单列是因为 §6 点名要覆盖三百万字符路径 |
| 2 | 首次 / 二次相同查询 | 墙钟 · 成对 | 经 HTTP 端点量，含 FastAPI 路由与 JSON 序列化。**必须成对读**：`lru_cache` 的收益是两者的差，不是任何一个的绝对值 |
| 3 | 峰值 RSS | 内存 | `resource.getrusage(RUSAGE_SELF).ru_maxrss`，**按平台换算成字节**（macOS 是字节，Linux 是 KiB）。本次在 macOS 上测，读作字节。峰值只增不减，所以表里是累积值，不是各阶段增量 |
| 4 | 反序列化次数 | **计数器** | 数的是**真正的 unpickle 次数**，不是 `load_book_cached()` 的调用次数（后者含缓存命中）。三处 loader 各自计数 |
| 5 | 归一化次数 | **计数器** | `search_service._normalize_with_map` 的调用次数与归一化字符总量 |
| 6 | 首页 TTFB × 书库规模 | 墙钟 × 自变量 | 冷进程里首页的第一个响应，**含 Jinja 模板渲染，不含解释器启动与 import**。排除 import 是因为它与书库规模无关，算进来会给曲线加一个两百毫秒的常数项，把线性关系压成一条看起来很平的线 |

计数器怎么装的：在基准脚本里包装三个模块各自的 `_Reader3Unpickler` 与
`search_service._normalize_with_map`，**不改 `src/` 下任何一行**。为了好测去改被测代码，
测到的就不是生产行为了。

## 3. 实测结果（2026-08-24，repeat=7，中位数 [min – max]）

### 指标 1 · 冷启动（20 本书，全新进程，不含 EPUB 解析）

| 分段 | 中位数 | 全距 | 相对全距 |
|---|---|---|---|
| 整体墙钟（含解释器启动） | **310.2 ms** | 293.7 – 358.7 | ±20.9% |
| `import reader3_app.web.server` | 203.4 ms | 189.9 – 230.8 | ±20.1% |
| `import TestClient` | 28.8 ms | 26.6 – 33.8 | ±24.8% |
| startup：`book_uuid_resolver.scan()` | 4.6 ms | 4.3 – 5.9 | ±34.1% |
| **可服务第一个请求** | **237.0 ms** | 221.3 – 269.8 | ±20.4% |
| 首页第一个响应 | 8.8 ms | 8.5 – 10.2 | ±19.7% |
| 峰值 RSS | 64.2 MiB | 63.9 – 64.3 | ±0.7% |

**冷启动的成本 86% 在 import 上**（203 / 237 ms），与书库规模无关。Phase 5 想改善启动
体验，该盯的是依赖树，不是扫书库那 4.6 ms。

> **为什么选「全新进程」这个口径。** 另一种口径是同进程内 `cache_clear()` 三处
> `@lru_cache`。它更稳（没有解释器启动噪声），但它测不到 import，而 import 恰恰是冷启动
> 里最大的一块。§6 说这项是给「Phase 5 的启动体验」做对照的——用户按下 `reader3-server`
> 之后等的是前者，不是后者。代价是方差更大（±20%），这一点写在 §4 的门禁结论里。

### 指标 1b · 大部头入库（源 3,000,000 字符 → 落盘 3,000,008 字符）

| 项 | 中位数 | 全距 |
|---|---|---|
| `process_epub()` | **47.4 ms** | 42.3 – 49.3（±14.8%） |
| 产出 `book.pkl` | 5.7 MiB | — |
| 源 `.epub` | 11.5 KiB | — |
| 峰值 RSS | 92.2 MiB | 92.0 – 92.5 |

11.5 KiB 的 EPUB 展开成 5.7 MiB 的 pickle，是因为合成语料是一句话重复三百万字符、zip
压缩率极高；**真实书的压缩比远没这么夸张，别拿这个比例外推**。这里要留档的是
「三百万字符走完解析 + 清洗 + 落盘约 47 ms」这个量级。

### 指标 2 · 首次查询 vs 二次相同查询

| 场景 | 首次 | 二次（完全相同的查询） | 加速比 |
|---|---|---|---|
| 全库搜索 · 20 本 + 1 本大部头 | 1188.8 ms | 1242.7 ms | **1.0×** |
| 书内搜索 · 小书（8 章 × 2000 字符） | 21.2 ms | 15.5 ms | 1.4× |
| 书内搜索 · 大部头（3M 字符） | 1189.0 ms | 99.2 ms | **12.0×** |

**全库搜索的第二次一分钱都没省。** 原因不是缓存没生效，是
`search_service.load_book_index` 的 `maxsize=4` 小于书库规模：跑完一轮 21 本，缓存里只
剩最后 4 本，下一轮从头再算。指标 5 的逐步计数给了同一件事的确凿证据（三轮相同的全库
搜索，每轮都是 180 次归一化，一次复用都没有）。

三对的「首次」都是真冷的：脚本刻意把全库搜索排在最前，让它把 `maxsize=4` 的缓存冲干净，
之后的小书与大部头才保证已被淘汰。顺序排错会配出一个假的加速比。

### 指标 3 · 峰值 RSS（累积；`ru_maxrss` 只增不减，不可分解成增量）

| 断点 | 中位数 | 全距 |
|---|---|---|
| 解释器 + 基准脚本 | 20.5 MiB | 20.4 – 20.7 |
| ＋ import 服务端 | 61.5 MiB | 61.4 – 61.8 |
| ＋ 首页（20 本 unpickle） | 72.9 MiB | 72.8 – 73.2 |
| ＋ 全库关键词搜索 | **236.7 MiB** | 236.5 – 237.0 |
| ＋ 大部头搜索（3M 字符） | **331.2 MiB** | 330.8 – 332.9 |

**这项是六项里最稳的（±0.2%～1.4%），也是 Phase 3 最可能退化的一项。** 台阶在哪很清楚：
20 本小书全部载入内存只花 11 MiB，而**搜索一本三百万字符的书要多花约 160 MiB**——见 §5
的发现 3。

### 指标 4 · 反序列化次数（一段典型操作序列，20 本书）

序列是照着「什么样的序列能让重复暴露出来」倒推的，不是随手挑的：

1. 打开书库首页（20 本 > `web.server.load_book_cached` 的 `maxsize=10`）
2. 打开**书库里第一本**的阅读页（保证已被 LRU 淘汰，不是碰运气挑一本）
3. 在这本书里搜一次（触发 `search_service` 的**另一份**缓存）
4. 回到书库首页
5. 用同一个词全库搜三次（20 本 > `load_book_index` 的 `maxsize=4`）

| loader | 次数 | 全距 |
|---|---|---|
| `web/server.py::load_book_cached` | 40 | 40 – 40（±0%） |
| `search_service.py::load_book_cached` | 60 | 60 – 60（±0%） |
| `vector_search.py::BookVectorIndex._load_book` | 0 | 0 – 0 |
| `pickle.load` 兜底路径（旧模块路径） | 0 | 0 – 0 |
| **合计** | **100** | **100 – 100** |

逐步增量（这张表比总数有用）：

| 步骤 | 增量 |
|---|---|
| `00_startup` | — |
| `01_library_page` | `web.server` +20 |
| `02_reader_page` | `web.server` **+1** ← 刚载入过的书，缓存里已经没了 |
| `03_in_book_search` | `search_service` **+1** ← **同一本书，第二处 loader 又解一遍** |
| `04_library_page_again` | `web.server` +19 |
| `05_library_search_1` | `search_service` +19 |
| `05_library_search_2` | `search_service` +20 |
| `05_library_search_3` | `search_service` +20 |

**一段只碰了 21 本不同的书的会话，做了 100 次 unpickle。** 这就是技术栈计划 A5「三处
loader 合并」要拿的直接指标；011 之后重跑，这个数应该显著下降。

`vector_search` 的 0 **是「本序列没走到」而不是「这处 loader 是死代码」**：语义检索路径
需要 chromadb 索引，本基准全程走关键词路径。JSON 里的 `vector_search_instrumented: true`
表明它确实被装了计数（装不上时脚本报的是缺项而不是 0，两者不能混）。

### 指标 5 · 归一化次数 `_normalize_with_map`

| 项 | 值 | 全距 |
|---|---|---|
| 调用次数 | **549** | 549 – 549（±0%） |
| 归一化字符总量 | **984,052** | 同上 |

拆解：一次全库搜索 = 20 本 × 8 章 = 160 次（正文）＋ 20 次（查询词，每本一次）= 180 次。
**三轮相同的搜索是 3 × 180，没有任何复用。** 书库正文总量约 32 万字符，被原样归一化了
三遍；剩下的 9 次来自步骤 3 的书内搜索。

> 这项要暴露的正是重复计算，所以序列非得是「同一批书搜多次」不可。只搜一次的话，计数就
> 等于「必要开销」，看不出任何浪费——那才是真正「测了个寂寞」。

### 指标 6 · 首页冷启动 TTFB × 书库规模

| 书库规模 | TTFB 中位数 | 全距 | 每本 ms |
|---|---|---|---|
| 1 本 | 7.5 ms | 7.3 – 7.6 | 7.53 |
| 5 本 | 7.8 ms | 7.6 – 7.9 | 1.56 |
| 10 本 | 8.1 ms | 7.8 – 8.3 | 0.81 |
| 20 本 | 8.6 ms | 8.4 – 8.7 | 0.43 |
| 40 本 | 9.7 ms | 9.4 – 10.0 | 0.24 |
| 80 本 | 12.4 ms | 12.0 – 12.8 | 0.15 |
| 160 本 | 18.3 ms | 17.9 – 19.0 | 0.11 |

最小二乘拟合：**`ttfb ≈ 7.32 ms + 0.0672 ms × n`，R² = 0.9964**。

**读数：线性，不是常数。** 但常数项（7.3 ms，模板渲染与首个请求的固定成本）在 n ≤ 40 时
压着线性项，所以只取到 20 本会看成一条平线。取到 160 本，斜率就没法否认了——这正是这项
指标必须是一条曲线而不是一个点的理由。0.067 ms/本 与指标 4 的「首页每次 unpickle N 本」
是同一件事的两种量法，互相印证。

## 4. 方差：哪几项现在还不配设门禁

任务书说「基准只记录、不设阈值门禁，性能回归门禁等有了多次运行的方差数据再谈」。
**下面这张表就是那份方差数据**，来自 4 次完整运行（同机、同参数、同一小时内）。

跨运行中位数（run1 / run2 / run3 / 记录之运行）：

| 指标 | run1 | run2 | run3 | 记录 | 跨运行漂移 |
|---|---|---|---|---|---|
| 冷启动 可服务 (ms) | 229.5 | 231.8 | 240.2 | 237.0 | ±4.6% |
| `process_epub` 3M (ms) | 45.8 | 47.3 | 47.1 | 47.4 | ±3.4% |
| 全库搜索 首次 (ms) | 1205.0 | 1188.6 | 1217.9 | 1188.8 | ±2.4% |
| 大部头 二次 (ms) | 100.7 | 101.5 | 102.5 | 99.2 | ±3.3% |
| 峰值 RSS 终值 (B) | 347,570,176 | 347,193,344 | 347,373,568 | 347,308,032 | ±0.1% |
| TTFB n=20 (ms) | 9.0 | 9.1 | 8.9 | 8.6 | ±5.6% |
| 反序列化合计 | 100 | 100 | 100 | 100 | **0** |
| 归一化调用 | 549 | 549 | 549 | 549 | **0** |

结论，分三档：

**✅ 现在就可以设门禁的：指标 4、5（两个计数器）。** 四次运行、每次 7 遍，28 个采样全部
逐位相同。它们是纯逻辑量，与机器、电源、负载都无关。**011 合并 loader 之后，把
`unpickle_grand_total ≤ 100` 和 `normalize_calls ≤ 549` 钉成断言是合理的**——它们变了
一定是代码变了。（本分支不设，因为任务书 §6 说了只记录；但这两项已经具备条件，写在这里
是为了 011 那条分支不用重新论证一遍。）

**🟡 可以设一个宽松门禁的：指标 3（峰值 RSS）。** 单次运行内 ±0.2%～1.4%，跨运行 ±0.1%，
是六项里最稳的墙钟外指标。**Phase 3 换存储格式时，「终值不得超过 400 MiB」这类粗阈值是
可执行的**，但别设 ±5% 这种精细阈值：不同机器的解释器基线本身就差十几 MiB。

**❌ 现在不配设门禁的：指标 1、1b、2、6（全部墙钟类）。** 理由不是「数字难看」，是
**噪声大于想守住的回归幅度**：

- 单次运行内的相对全距普遍在 ±10%～35%，`import TestClient` 一项到过 ±68%。
- 更要命的是**离群点**：run2 的 TTFB@40 本有一个 291 ms 的采样（中位数 11.2 ms，26 倍），
  run2 的 TTFB@20 本有一个 27.6 ms 的采样。中位数把它们吸收了，任何「单次运行超阈值就红」
  的门禁会被它们打成天天误报。
- run3 更直白：机器负载升到 6.5 时，TTFB 曲线的 R² 从 0.997 掉到 **0.15**，斜率从
  0.075 掉到 0.033。**同一份代码，什么都没改。** 一个建立在这条曲线上的门禁，那天会宣告
  「O(n) 扫描被修复了」。（run1–run3 的曲线取样点是 `1,5,10,20,40`，记录之运行是
  `1,5,10,20,40,80,160`；R² 的对比在 run1 与 run3 之间是同参数的，可比。）

要让墙钟类指标够得着门禁，需要的不是更严的阈值，是更干净的测量环境：插电、静默机器、
固定 CPU 亲和，并且**比中位数而不是比单次**。在拿到那样的环境之前，这四项继续只记录。

## 5. 过程中发现的现状问题（**只记录，不修**）

1. **A5 的「三处 loader」有了确凿证据，且比预想的更贵。** 一段只碰 21 本书的会话做了
   100 次 unpickle。其中步骤 3 的那一次是最干净的实锤：`web/server.py` 刚刚
   unpickle 过的同一本书，`search_service.py` 立刻又从磁盘解了一遍——两处各自持有
   `maxsize=10` 的 `lru_cache`，互相看不见对方。
   *严重度：中（性能，非正确性）。归属：011。*

2. **`library_view` 的 `lru_cache` 命中率是 0%——不是「偏低」，是零。**
   `web.server.load_book_cached` 是 `maxsize=10`，首页每次顺序扫全部 20 本。**顺序扫一
   个长于缓存的序列，是 LRU 的最坏情况**：扫到第 11 本时淘汰第 1 本，下一轮回到第 1 本时
   它刚好不在——每一本都在「即将被用到」的前一刻被踢掉。这不是概率问题，是必然的，且轮数
   再多也不会好转：

   ```
   $ python3 -c '...maxsize=10, 顺序扫 20 本, 扫 3 轮...'
   第 1 轮：miss 20/20   第 2 轮：miss 20/20   第 3 轮：miss 20/20
   CacheInfo(hits=0, misses=60, maxsize=10, currsize=10)
   ```

   指标 4 里那个 19（而不是 20）是唯一的例外，来自步骤 2 刚读过的那本书被顶到了 MRU 位置。
   一次「开首页 → 读一本 → 回首页」＝ 20 ＋ 1 ＋ 19 ＝ 40 次 unpickle，缓存一次没派上用场，
   却还占着 10 本书的内存。

   **⚠️ 给 011 的警告：不要用「把 `maxsize` 调到 20」来修。** 那只是把悬崖挪到第 21 本，
   而书库规模是用户定的。要么让首页别去 unpickle 整本书（它只需要元数据——这是 012 换存储
   格式的动机之一），要么换一个对顺序扫不敏感的策略。LRU 在这种循环访问下**比随机淘汰还差**
   （随机能拿到约 50%），所以「缓存小了」这个诊断会把人引到错误的修法上。
   *严重度：中。归属：011 / 012。*

3. **`_normalize_with_map` 的 `index_map` 是每字符一个 Python int 的 list，是内存大头。**
   实测：对一段 3,000,000 字符的文本调一次，峰值 RSS 涨 **158.9 MiB**（其中 list 的指针
   数组占 23.3 MiB，其余是 300 万个 int 对象）。这解释了指标 3 里 236.7 → 331.2 MiB 那级
   台阶。**Phase 3 换存储格式时这是最可能退化、也最有得赚的一处**：换成 `array('i')` 或
   只在有归一化差异处记录偏移，能省掉绝大部分。
   *严重度：中高（内存）。归属：012。*

4. **`load_book_index` 的 `maxsize=4` 让「重复的全库搜索」完全没有缓存收益。** 指标 2 的
   全库加速比 1.0×、指标 5 的三轮各 180 次归一化，是同一件事的两个证据。用户连续搜同一个
   词两次，第二次和第一次一样贵。**成因与第 2 条同构**（顺序扫 20 本 > `maxsize=4`），修法
   同样不是把 4 调大——同一条警告适用。
   *严重度：中。归属：011。*

5. `web/server.py:148` 用 `print()` 报告坏掉的 `book.pkl`，不是 `logger`。该处已有的
   `# noqa` 注释里也写了同一句。基准跑到时会把它打进 stdout——本脚本用行前缀
   （`@@BENCH@@`）而不是整份 stdout 解析结果，就是为了不被它污染。
   *严重度：低。归属：011。*

## 6. 本次没做到的部分

- **只在一台机器、一种电源状态下测过。** 电池 + 半载。跨机对比（尤其 Linux CI）需要
  重跑一次；`ru_maxrss` 的单位分支在脚本里已经写了，但 **Linux 侧从未被真的执行过**。

  秒量级，不属于「可重跑的基准」这个形状。指标 4 里它的计数因此恒为 0，已在 §3 注明。
- **没有做多并发下的测量。** 六项全是单请求串行。FastAPI 的线程池行为、`lru_cache` 在并发
  下的重复计算，都不在这份基线里。
